# stride 算法深入
## stride 算法原理非常简单，但是有一个比较大的问题。例如两个 pass = 10 的进程，使用 8bit 无符号整形储存 stride， p1.stride = 255, p2.stride = 250，在 p2 执行一个时间片后，理论上下一次应该 p1 执行。
## 实际情况是轮到 p1 执行吗？为什么？
  * 是p2执行
  * p2 执行后，stride += pass = 250 + 10 = 260。
  * 8 位无符号整数溢出后，260 % 256 = 4，因此 p2.stride = 4。
  * 此时 p1.stride = 255，p2.stride = 4。
  * 按数值比较，4 < 255，所以 p2 会再次执行，而非预期的 p1。
## 我们之前要求进程优先级 >= 2 其实就是为了解决这个问题。可以证明， 在不考虑溢出的情况下 , 在进程优先级全部 >= 2 的情况下，如果严格按照算法执行，那么 STRIDE_MAX – STRIDE_MIN <= BigStride / 2。
## 为什么？尝试简单说明（不要求严格证明）。
  * P.pass = BigStride / P.priority , 在priority >=2的情况下，pass <= BigStride / 2
  * 不考虑溢出，初始stride=0，每次+pass <= BigStride / 2，每次执行最小，所以两个stride之间的最大差只有pass大小则<= BigStride / 2

## 已知以上结论，考虑溢出的情况下，可以为 Stride 设计特别的比较器，让 BinaryHeap<Stride> 的 pop 方法能返回真正最小的 Stride。补全下列代码中的 partial_cmp 函数，假设两个 Stride 永远不会相等。 
  ```rust
  use core::cmp::Ordering;

  const BIG_STRIDE: u64 = 255;

  impl PartialOrd for Stride {
      fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
          let diff = self.0.wrapping_sub(other.0);
          // 通过这个判断，来判断这两相比较是否处于溢出边界附近，则即将溢出的一侧(比如已经255)应该认为是上一轮的遗留，而另一侧是已经溢出过的下一轮数据(比如很小的4)
          // 一个比较形象的比喻，关于时钟的晚上9点和凌晨1点，凌晨一点应该认为是较大的那个，此时应该调度晚上9点的任务
          // 相对的，如果差值小于BIG_STRIDE / 2，认为两个数据处于表盘的同侧，可以直接比较大小
          if diff <= BIG_STRIDE / 2 {
              Some(self.0.cmp(&other.0))
          } else {
              Some(other.0.cmp(&self.0))
          }
      }
  }
  ```
